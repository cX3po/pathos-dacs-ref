# pathos-dacs partner kit — self-contained DACS conformance sanity vectors

A **non-normative** conformance sanity kit for DACS implementers, extracted from
[`pathos-dacs-ref`](../../README.md) (an independent reference implementation of the
DACS — Demos Agent Commerce Standards — paper v0.7 / DACS-1..5 v0.1).

Copy this directory anywhere, then:

```bash
node run-conformance.mjs           # human-readable report
node run-conformance.mjs --json    # machine-readable report
```

**Requirements for the run path: Node ≥ 18. Nothing else.** `run-conformance.mjs` and the
`.mjs` modules it loads need no `npm install`, no network, and import nothing outside this
directory (crypto comes from `node:crypto`; the RFC 8785 serializer is an original
implementation in `jcs.mjs`). The one exception is `generate.mts`: it is REPO-SIDE tooling
that regenerates `vectors.json`/`MANIFEST.json` from the reference implementation and only
runs inside the `pathos-dacs-ref` repo (it imports the src tree + dev deps). It ships in
the kit solely so the directory is fully tamper-evident — you never need to run it.

## What passing means — honest scope

Passing all **49 declared vectors** means your copy of this kit reproduces the
pathos-dacs-ref reference behavior on the covered surfaces. It does **not** mean your
implementation is "DACS certified" — no such certification exists, this kit is not
normative, and the normative source of truth is the DACS specification itself. The kit
covers exactly:

| Section | Vectors | Surface |
|---|---|---|
| `canonical-accept` | 22 | RFC 8785 JCS + DACS §B.2 pre-pass: canonical bytes AND sha256 must match byte-for-byte |
| `canonical-reject` | 5 | The five canonical reject constructors (2^53 boundary, large magnitude, 1e21 DACS-tightening, lone surrogate, BigInt) — a conforming canonicaliser MUST reject each. NFC key collision was removed: member names are no longer normalised, so an NFC/NFD name pair cannot collide and is now a canonical-accept case |
| `domain-sep-sign` | 12 | §B.7 closed-registry domain separation: sign/verify roundtrips (reference-generated signatures must reproduce), closure rules (unknown separator fails; read-only legacy separators verify but never sign), composite `signed_bytes` layout |
| `drift-signed-scope` | 10 | DACS-5 §10.4.1/R5-1 bundle signed-scope hash + DACS-4 evidenceHash drift semantics, incl. fail-closed manifest handling |

The drift section's structural check is a documented **subset** of the reference
verifier (`src/lib/verify-bundle-v1.ts`, ~700 lines) — row-for-row parity with the
reference evaluator over these vectors was asserted at generation time (see
`MANIFEST.json.parityReceipt`). A kit "accept" is not a full §10.4 verification.

To check your OWN fixtures (not just these vectors), use the full repo's `dacs-drift`
CLI or the `dacs-drift` GitHub Action — see `../../CONFORMANCE.md`.

## Integrity

`MANIFEST.json` carries a sha256 for every file in the kit plus full provenance (source
commit of pathos-dacs-ref, per-source-file hashes, generation timestamp, and the exact
command + result receipt of the generation-time self-run). The runner verifies the
per-file hashes before executing and **fails closed** (exit 3) on any mismatch;
`--allow-modified` runs anyway with a loud warning that results are no longer
attributable to the published kit.

Test keys embedded in `vectors.json` are **deterministic, publicly-derivable TEST
vectors** (sha256 of a published label string) — they are not secrets and must never be
used for anything but these vectors.
